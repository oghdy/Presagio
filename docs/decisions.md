## D-001 프로젝트를 "역할을 나눈 여러 에이전트 세션(회사 구조)"으로 진행한다
- **날짜:** 2026-10-21
- **무엇을:** PM, Data Engineer, ML Engineer, Leakage Auditor, Backend Engineer, Platform Engineer, Reviewer, Scribe 8개 역할을 정의하고, 사람이 최종 결정권자가 된다. 역할 정의는 `.claude/agents/`, 운영 규칙은 `docs/team/`.
- **왜:** 단계 0~6을 한 세션으로 하면 컨텍스트가 너무 길어져 품질이 떨어지고, 작성자가 자기 코드를 검증하는 구조가 된다. 역할을 나누면 (1) 영역별 맥락이 짧게 유지되고 (2) 리뷰와 누수 검증이 작성자와 분리되고 (3) 면접에서 "팀 프로세스를 설계해 봤다"는 이야기가 된다.
- **다른 선택지:** 한 세션으로 순차 진행(간단하지만 위 문제), 역할 없이 서브에이전트만 사용(검증 독립성이 약함).
- **다시 볼 때:** 단계 1 종료 시 토큰 비용과 핸드오프 실패 횟수를 보고 역할 수를 조정한다.

## D-005 모든 코드 변경은 브랜치 + PR + 독립 리뷰를 거치고, 머지는 사람이 한다
- **날짜:** 2026-10-21
- **무엇을:** `main` 직접 커밋 금지. 브랜치 이름 `feat/P-NNN-...`. PR마다 새 Reviewer 세션. squash merge 기본.
- **왜:** 리뷰어가 작성자 의견에 끌려가지 않게 하려면 세션을 분리해야 한다. 사람이 머지하는 이유는 "사람이 이해한 코드만 들어간다"를 보장하기 위해서다(포트폴리오 목적).
- **다른 선택지:** 자동 머지(빠르지만 사람이 코드를 모르게 됨).
- **보완(2026-10-22, 사람 결정):** 사람이 수락 메시지를 읽고 명시적으로 지시하면("머지해줘", "머지ㄱㄱ") PM이 `gh pr merge --squash`로 대신 실행할 수 있다. 리뷰어나 작업자는 머지하지 않는다. 사람이 이해하고 결정한다는 원칙은 그대로이고, 버튼을 누르는 손만 위임한 것이다.

## D-007 문서는 한국어, 코드와 커밋 제목은 영어

- **다른 선택지:** 전부 영어(학습 효율 저하), 전부 한국어(코드 가독성과 관례 문제).

## D-011 세션의 모델과 노력 수준은 역할과 티켓 성격으로 정한다
- **날짜:** 2026-10-21
- **무엇을:** 세션을 띄울 때 아래 표를 기본값으로 쓴다. 사람이 제안하고 PM이 보완해 확정했다.

  | 역할 / 티켓 성격 | 모델 | 노력 | 예시 |
  | --- | --- | --- | --- |
  | PM (장기 세션, 판단·조율) | Fable 5.1 | 높음 | PM 세션 |
  | 작업자, 실행형 티켓 | Opus 5.5 | 높음 | P-001, P-002, P-003, P-013~P-017 |
  | 작업자, 설계·조사형 티켓 | Opus 5.5 | 엑스트라(xhigh) | P-010, P-011 스키마 설계, P-018 배당 조사 |
  | Reviewer | Opus 5.5 | 높음 | 모든 PR |
  | Leakage Auditor (단계 2부터) | Fable 5.1 | 높음 | 누수 검증 |
  | Scribe (단계 4부터) | Sonnet 5.5 | 보통 | 학습 노트, README |

  조정 규칙: 같은 티켓이 2번 반려되면 다음 시도는 한 단계 올린다(Opus 높음 → Opus xhigh → Fable). 어떤 모델과 노력으로 띄웠는지는 PM이 backlog 티켓 메모에 적는다.
- **왜:** 실행형 티켓은 브리핑과 완료 기준이 이미 판단을 대신하므로 정확한 실행만 필요하고, 가장 비싼 모델을 쓰는 것은 토큰 낭비다(`docs/team/risks.md` A2). 반대로 "무엇을 만들지 정하는 일"(설계, 조사)과 "틀린 것을 잡는 일"(누수 감사)은 판단력이 결과를 좌우하므로 여기서 아끼면 나중에 더 비싸게 돌아온다. PM은 장기 세션에서 조율과 수락 판단을 하므로 가장 센 모델을 유지한다.
- **다른 선택지:** 전부 Fable(비용 과다), 전부 Opus 고정(설계·감사 품질 위험), 티켓마다 사람이 매번 지정(사람의 결정 부담 증가). 표로 기본값을 두고 예외만 사람이 결정하는 쪽을 택했다.
- **다시 볼 때:** 단계 1 종료 시 반려 횟수와 토큰 비용을 보고 표를 조정한다. Opus 높음으로 돌린 티켓이 반복 반려되면 그 성격의 티켓을 xhigh로 올린다.

## D-012 비밀값 탐지 훅은 gitleaks를 쓴다
- **날짜:** 2026-10-21 (P-001, PR #1의 결정 제안을 PM이 채택)
- **무엇을:** `.pre-commit-config.yaml`에 `gitleaks/gitleaks` 훅(v8.30.1)을 넣는다. 커밋 시점에 스테이징된 변경에서 비밀값을 찾아 커밋을 막는다.
- **왜:** (1) baseline 파일이 필요 없다. detect-secrets는 `.secrets.baseline`을 만들고 오탐마다 갱신·커밋해야 해서 관리 파일이 하나 늘어난다. (2) GitHub/AWS/Slack 등 서비스별 규칙이 기본으로 많고, 가짜 `ghp_` 토큰을 `github-pat` 규칙으로 실제로 잡았다. 출력에서 비밀값을 가린다(`--redact`). (3) 같은 바이너리로 CI에서 기록 전체 검사(`gitleaks git`)도 할 수 있다.
- **다른 선택지:** detect-secrets(순수 파이썬, 엔트로피 탐지가 강하지만 baseline 관리 부담), `gitleaks-system`/`gitleaks-docker` 훅 변형(수동 설치 또는 Docker 필요).
- **알려진 한계:** pre-commit 훅은 `--staged`라 이미 커밋된 기록은 보지 않는다. `pre-commit run --all-files`에서 gitleaks가 통과해도 "레포에 비밀값이 없다"는 뜻이 아니다. 기록 전체 검사는 CI(P-003)에서 하기로 사람에게 제안했다(아래 승인 대기 표).

## D-013 파이썬은 uv 관리 3.12만 쓴다 (`only-managed`, `<3.13` 상한)
- **날짜:** 2026-10-21 (P-001, PR #1의 결정 제안을 PM이 채택)
- **무엇을:** `pyproject.toml`에 `requires-python = ">=3.12,<3.13"`과 `[tool.uv] python-preference = "only-managed"`를 둔다. `.python-version`은 `3.12`.
- **왜:** 이 맥에서는 기본 설정이면 anaconda 파이썬이 먼저 잡힌다(`docs/team/risks.md` B8, 작업자가 `uv python find 3.12`로 실제 확인). `only-managed`로 uv가 내려받은 CPython만 쓰게 해 환경 차이를 없앤다. 상한을 둔 것은 완료 기준 "3.12로 고정"을 글자 그대로 지키기 위해서다.
- **다른 선택지:** `python-preference = "managed"` 기본값(시스템 파이썬으로 떨어질 수 있음), `requires-python = ">=3.12"`(3.13에서도 설치됨).
- **다시 볼 때:** 의존 라이브러리(LightGBM 등)가 3.13을 요구하거나 3.12 지원을 끊을 때.

## D-014 리뷰어 세션의 worktree는 main에서 만들어지므로 브리핑에 PR 체크아웃 단계를 넣는다
- **날짜:** 2026-10-21 (P-001 리뷰에서 발견한 프로세스 문제)
- **무엇을:** 리뷰어 브리핑에 반드시 다음을 넣는다: `git fetch origin <브랜치> && git checkout --detach origin/<브랜치>`, 그리고 `git diff main...HEAD --stat`이 비어 있지 않은지 확인. 작업자 브랜치는 작업자 worktree에 체크아웃되어 있어 일반 checkout이 거부되므로 detached로 받는다.
- **왜:** 앱이 만드는 worktree는 항상 main 기준이다. 리뷰어가 diff가 비어 있는 것을 놓치면 "리뷰할 것 없음"이라는 빈 리뷰가 나올 수 있다. P-001 리뷰어는 스스로 알아챘지만 운에 맡기지 않는다.
- **다른 선택지:** 리뷰어를 작업자 worktree에서 돌리기(작업자 환경에 영향, 독립성 약화), 공유 체크아웃에서 브랜치 전환(PM 체크아웃이 바뀜).

## D-015 비밀값 기록 전체 검사는 CI에서 한다 (P-003 완료 기준 추가)
- **날짜:** 2026-10-22 (사람 승인: "결정 1,2,3은 추천대로 진행바람")
- **무엇을:** P-003(GitHub Actions CI)의 완료 기준에 "`gitleaks git`으로 커밋 기록 전체 검사 통과"를 추가한다. README에는 "pre-commit의 gitleaks 훅은 스테이징된 변경만 본다, 기록 전체는 CI에서"를 한 줄 적는다(P-003 범위).
- **왜:** pre-commit 훅은 `--staged`라 이미 커밋된 비밀값이나 `--no-verify`로 우회한 커밋을 잡지 못한다(P-001 리뷰에서 재현). 두 겹으로 막는다: 커밋 시점(pre-commit)과 PR 시점(CI).
- **다른 선택지:** pre-commit 훅 하나로 충분하다고 보기(우회 가능), GitHub secret scanning만 믿기(공개 레포 기본 기능이지만 패턴 범위가 다르고 로컬에서 재현 불가).
- **비고:** 완료 기준 변경은 사람만 할 수 있다(D-008). 이 건은 리뷰어 제안 → PM 추천 → 사람 승인 순서로 바뀌었다.

## D-016 로컬 Docker 런타임은 Docker Desktop을 쓴다
- **날짜:** 2026-10-22 (사람 결정, Q-003)
- **무엇을:** 개발 맥에 Docker Desktop(4.96.2, Docker Engine 29.9.2, Compose v5.6.1)을 설치했다. `docker compose up`으로 PostgreSQL을 띄운다(P-002).
- **왜:** 개인 용도 무료, 가장 표준적인 도구라 README의 `docker compose up`이 어디서나 같은 뜻이고 면접관도 아는 도구다. GUI로 컨테이너 상태를 눈으로 확인할 수 있어 학습용으로도 낫다.
- **다른 선택지:** OrbStack(가볍고 빠르지만 상업 이용은 유료, 맥 전용), Colima(오픈소스 무료, CLI만, 설정이 더 필요).
- **다시 볼 때:** 맥 메모리 부담이 크면 OrbStack으로 바꿀 수 있다. compose 파일은 그대로 쓸 수 있으므로 전환 비용은 낮다.

## D-017 레포를 공개(public)로 전환한다
- **날짜:** 2026-10-22 (사람 결정, Q-004)

- **따라오는 규칙:** 공개 레포이므로 `.env`, API 키, 실제 배당 데이터 덤프를 더욱 커밋하면 안 된다. pre-commit gitleaks(D-012) + CI 기록 전체 검사(D-015) 두 겹이 그 방어선이다. 외부 API 키는 GitHub Secrets에만 둔다(단계 6).

## D-018 CI 비밀값 검사는 gitleaks 바이너리를 직접 실행하고, 가져온 모든 브랜치의 기록을 검사한다
- **날짜:** 2026-10-22 (P-003, PR #2의 결정 제안 + 리뷰어 검증을 PM이 채택)
- **무엇을:** `.github/workflows/ci.yml`의 `secret-scan` 잡은 gitleaks v8.30.1 공식 릴리스를 sha256 체크섬 검증 후 받아 `gitleaks git --redact .`를 실행한다. `actions/checkout`은 `fetch-depth: 0`. 서드파티 액션은 커밋 SHA로 고정한다. 검사 범위는 **checkout이 가져온 모든 ref(원격 브랜치 전체)의 커밋 기록**이다(리뷰어가 재현으로 확인. 작성자의 처음 설명 "HEAD만 본다"는 틀렸고 PR에서 정정했다).
- **왜:** (1) pre-commit 훅과 같은 버전·같은 규칙이라 "로컬 통과 = CI 통과"가 보장된다. (2) 로컬에서 같은 명령으로 재현된다. (3) `gitleaks-action`은 자체 라이선스이고 조직 이전 시 키가 필요하다. (4) 모든 브랜치를 보는 것은 공개 레포에서는 어느 브랜치든 올라가면 이미 노출이므로 넓게 울리는 쪽이 맞다.
- **대가:** 원격의 어느 브랜치 하나에 비밀값(또는 오탐)이 있으면 무관한 PR까지 전부 `secret-scan`이 실패한다. 그 브랜치를 지우거나 고쳐야 머지가 풀린다. 카나리 브랜치는 반드시 바로 지운다.
- **다른 선택지:** `gitleaks/gitleaks-action@v3`(PR 댓글·SARIF 편리, 라이선스 의존), `--log-opts=HEAD`로 PR 기준만 검사(좁지만 다른 브랜치 유출을 못 봄), GitHub secret scanning(공개 레포에서 켤 수 있음, 로컬 재현 불가. 켜는 것은 사람 몫).
- **후속:** `concurrency.cancel-in-progress`가 `push: main`에도 적용되어 연속 머지 시 앞 커밋의 CI가 취소될 수 있다(리뷰어 [낮음]). 단계 1에서 CI에 postgres service container를 붙일 때 같이 고친다.

## D-019 DB 접속 스택: psycopg 3 + SQLAlchemy 2 + pydantic-settings, `DATABASE_URL` 한 줄, postgres 17, 호스트 포트 5433
- **날짜:** 2026-10-22 (P-002, PR #4의 결정 제안을 PM이 채택)
- **무엇을:**
  - 드라이버 psycopg 3(`psycopg[binary]`), URL `postgresql+psycopg://`. 동기 SQLAlchemy 2.x 공식 지원 현행 드라이버, psycopg2의 후속, 바이너리 휠이라 libpq 설치 불필요, 나중에 async도 같은 드라이버.
  - 설정은 pydantic-settings `BaseSettings`: `.env` 읽기, 환경변수 우선, 타입 변환·검증, 필수값 누락 시 즉시 에러. 단계 5 FastAPI와 같은 생태계.
  - 파이썬은 `DATABASE_URL` 한 줄(SQLAlchemy·Alembic·PaaS 표준), 컨테이너는 `POSTGRES_*` 개별 변수(이미지가 그렇게 받음). 같은 정보가 두 곳에 있으므로 함께 고친다.
  - 이미지 `postgres:17-alpine`: "16 이상" 중 데이터 경로가 16과 같은 마지막 메이저, 지원 2029-11. 18은 볼륨 경로 규칙이 바뀜(작성자가 `docker image inspect`로 확인).
  - 호스트 포트 5433, `127.0.0.1` 바인딩: 이 맥의 Postgres.app이 5432를 쓰고 있고, 같은 네트워크의 다른 기기가 가짜 비번으로 접속하지 못하게.
- **다른 선택지:** psycopg2-binary(유지보수 모드), asyncpg(async 전용, Alembic·배치와 안 맞음), `os.environ` 직접(검증 없음), 개별 변수로 URL 조립(PaaS와 안 맞음), postgres 16(보수적)/18(최신, 경로 다름), 포트 5432(충돌).
- **skip 기준:** D-020에 따로 적었다.

## D-020 DB 연결 테스트는 "아무도 안 들음"이면 skip, "들었는데 거부함"이면 실패한다
- **날짜:** 2026-10-22 (P-002 리뷰 과정에서 확정)
- **무엇을:** `tests/conftest.py`의 `db_engine` fixture는 (1) `DATABASE_URL`이 없으면 skip, (2) TCP 탐침으로 포트에 아무도 안 들으면 skip(연결 거부, 타임아웃 2초), (3) 포트는 열렸는데 DB가 거부하면(비밀번호 틀림, DB 없음) **실패**시키고 원인 메시지 전체를 보여준다. `PRESAGIO_REQUIRE_DB=1`이면 skip 대신 전부 실패. 실패 경로에서 비밀번호가 traceback에 찍히지 않도록 `__tracebackhide__`를 쓰고, "출력에 비밀번호 없음"을 테스트로 고정한다.
- **왜:** 환경변수 유무만 보면 ".env는 있는데 Docker를 안 켠" 개발자의 테스트가 실패해 완료 기준 4("DB 없이도 통과")를 어긴다. 반대로 모든 연결 오류를 skip하면 볼륨 생성 후 비밀번호를 바꾼 것 같은 실제 설정 오류가 "DB 꺼짐"으로 위장되어 조용히 넘어간다(리뷰어 재현). pytest는 기본 traceback에 함수 인자를 찍으므로 URL 문자열을 받는 프레임에서 실패하면 비밀번호가 노출된다(리뷰어 재현, `grep -c WRONGPW` 4 → 수정 후 0).
- **다른 선택지:** pytest 마커(`-m db`)로 분리(기본 실행에서 빠져 잊기 쉬움), 환경변수 유무만 보기, 모든 OperationalError를 skip.
- **알려진 한계(단계 1에서):** fixture가 function 범위라 응답 없는 호스트에서는 DB 테스트마다 2초씩 늘어난다(지금 6개 → 약 12초). "닿는지" 판정을 session 범위로 한 번만 하는 방식을 단계 1 DB 티켓에서 다룬다. CI에 postgres service container를 붙일 때 `PRESAGIO_REQUIRE_DB=1`을 켠다(Q-005).

## D-024 nba_api 요청 기본값: 간격 1.0초, 타임아웃 10초, 백오프 3회, 403/429는 JSON 파싱 전에 검사해 즉시 중단
- **날짜:** 2026-10-22 (P-010 결정 제안 + 리뷰어 발견 사항을 PM이 채택)

## D-029 CI는 postgres service container로 실제 DB 테스트를 돌리고, main push 실행은 취소·교체되지 않는다
- **날짜:** 2026-10-22 (P-023, PR #8의 결정 제안 + 리뷰어 검증을 PM이 채택)
- **무엇을:** `lint-and-test` 잡 안에 `postgres:17-alpine` service container(포트 5433, 사용자/DB `presagio`, 워크플로 파일에 박힌 CI 전용 가짜 비밀번호 `ci-only-not-a-secret`)를 두고 `PRESAGIO_REQUIRE_DB=1`, `pytest -rs`로 돈다. (3) `cancel-in-progress: false`만으로는 같은 그룹의 **대기 중** 실행이 기본으로 교체되므로(GitHub 문서, 리뷰어가 원문 확인) main 그룹 자체를 분리해야 "머지 커밋마다 CI 한 번"이 보장된다. 실제로 2026-10-22 머지 커밋 `376e4d5`의 실행이 docs 푸시에 밀려 취소된 적이 있다.

- **다른 선택지:** 별도 `db-test` 잡(체크 이름 추가, 설치 중복), 비밀번호를 Secrets로(포크 PR 실패), `concurrency.queue: max`(main을 한 줄로 세움, 느림, 100개 제한), `cancel-in-progress`만 표현식(대기 교체 문제 남음).
- **검증 완료(2026-10-22):** PR #8 머지 커밋 `c7d88d1`과 7초 뒤 docs 커밋 `a923715`가 main에 연달아 들어갔고, 두 실행 모두 취소 없이 동시에 돌아 success로 끝났다. D-018 후속 과제 해결.

## D-030 마이그레이션 운영 규칙: 제약 이름 규칙, CHECK는 표 단위 + 드리프트 감지, 테스트는 임시 DB, 설계 DDL 일치 테스트
- **날짜:** 2026-10-22 (P-012, PR #9의 결정 제안 4건 + 리뷰어 검증을 PM이 채택)
- **무엇을:**
  1. **제약 이름 규칙:** `pk_<표>`, `fk_<표>_<컬럼>_<참조표>`, `uq_<표>_<컬럼들>`, `ck_<표>_<규칙이름>`. 인덱스는 설계안 이름 그대로(`ix_*`). 설계안이 이름을 준 유니크 3개는 보존. 에러 메시지의 `constraint_name`만으로 어떤 규칙이 막았는지 알 수 있게.
  2. **CHECK는 모델에서 항상 `__table_args__`(표 단위)로 선언.** Alembic autogenerate는 컬럼 인자로 넣은 `CheckConstraint`를 마이그레이션에 렌더하지 않고(작성자·리뷰어 재현), 기본 `alembic check`는 CHECK를 비교하지 않는다. 보완으로 `env.py`에 opt-in 플러그인 `alembic.ext.checkconstraint_byname`을 켜고(이름 기준 추가/삭제 감지), 모델 `create_all` 결과와 마이그레이션 DB의 CHECK 정의(`pg_get_constraintdef`)를 비교하는 테스트로 식 변경까지 잡는다.
  3. **마이그레이션 테스트는 임시 DB `<db>_test_<랜덤8자>`를 만들어 쓰고 지운다.** 개발 DB를 `downgrade base`로 비우지 않기 위해. `DATABASE_URL`의 사용자에게 `CREATEDB` 권한 필요(로컬 compose·CI 모두 슈퍼유저). 강제 종료 시 잔여 DB는 README의 정리 명령으로.
  4. **승인된 설계 DDL(`docs/design/schema-v1.md` 부록 A)과 마이그레이션 0001의 일치를 테스트로 고정.** 임시 DB 두 개에 각각 적용해 카탈로그(컬럼·타입·NULL·기본값·identity·생성 컬럼·제약 정의·인덱스 정의·뷰 정의)를 비교. "모델 = 마이그레이션"은 `alembic check`, "마이그레이션 = 설계"는 이 테스트가 본다.
- **왜:** 스키마는 Data ↔ ML 계약(D-004)이라 코드와 승인 문서가 조용히 어긋나는 것이 가장 큰 위험이다. 리뷰어의 변이 검사: 마이그레이션 CHECK 식 변경(M1)은 DDL 비교 테스트가, 인덱스 누락(M2/M3)은 `alembic check`가, 모델에서만 CHECK 식 변경(M4)은 처음엔 아무도 못 잡았다가 2번 보완 후 새 테스트가 잡는다.
- **다른 선택지:** PostgreSQL 기본 제약 이름(`games_check1`, 읽기 어려움), 컬럼 단위 CHECK + 수동 마이그레이션(다음 사람이 빠뜨림), 개발 DB에서 직접 테스트(데이터 생기면 위험), 별도 스키마(`search_path`, 뷰 정의가 복잡), 사람이 눈으로 DDL 대조(CHECK 60개).
- **교훈(테스트 환경):** 파이썬 시각과 DB `now()`를 비교하는 테스트는 Docker Desktop(VM 시계 약 1ms 느림)에서는 가끔만 실패하고 CI(시계 공유)에서는 거의 매번 실패한다. 시각은 한쪽(DB 또는 고정값)으로 통일한다. "로컬 흉내"는 CI 증명을 대신하지 못한다.

## D-031 nba_api는 "요청 설명"으로만 쓰고 전송은 우리 httpx 클라이언트가 한다
- **날짜:** 2026-10-22 (P-013, PR #10의 결정 제안 1~3 + 리뷰어 검증을 PM이 채택)
- **무엇을:** `nba_api_request(endpoint)`가 nba_api 엔드포인트 객체(`get_request=False`)에서 URL 템플릿·파라미터·기본 헤더만 읽어 `ApiRequest`를 만들고, `IngestionClient`가 httpx로 보낸다. nba_api의 `send_api_request`/`get_request()`는 쓰지 않는다. 그래서 `nba_api`는 런타임 의존성이다(pandas 3.0.6, numpy 2.5.4 동반). `Accept-Encoding`은 `gzip, deflate`로 고정한다(brotli 미설치 시 httpx가 `br` 응답을 압축된 채로 돌려줌, 리뷰어 재현).
- **왜:** (1) nba_api는 받은 바이트가 아니라 디코딩된 `response.text`를 주고 오류 본문을 XML로 바꾸기까지 해서 `response_sha256`(D-028 A-1)을 정직하게 만들 수 없다. (2) 엔드포인트가 전송 직후 JSON을 파싱해 상태 코드를 먼저 볼 수 없다(D-024). (3) nba_api와 The Odds API가 같은 전송·재시도·타임아웃·raw 저장 코드를 탄다. 리뷰어가 6개 엔드포인트의 URL·쿼리가 동일함을 오프라인 대조하고 실제 호출 1회로 같은 바이트를 확인했다.
- **다른 선택지:** nba_api를 그대로 쓰고 `nba_response._status_code`를 읽기(바이트 보존 불가, 파싱이 먼저), `NBAHTTP.set_session()`으로 세션 끼우기(제어 흐름이 nba_api 쪽), URL·헤더 하드코딩(nba_api 업데이트를 못 따라감), `brotli` 의존성 추가.
- **남은 위험:** 헤더 순서와 TLS 지문이 requests와 달라 차단 판정이 달라질 수 있다. 지금까지 실제 호출 3회 모두 200. 차단되면 `aborted`로 멈추므로 안전 쪽. `httpx` 로거를 import 시 WARNING으로 올려 쿼리스트링(키 포함) INFO 로그를 막았는데, CLI(P-016)가 `dictConfig`로 로깅을 설정할 때 이 레벨을 유지해야 한다.

## D-032 수집 레이어 운영 규칙: 모든 응답을 raw에 저장, 읽기는 2xx만, 차단은 `aborted`, 일시 오류에 연결 오류 포함, 시계는 표별로 다름
- **날짜:** 2026-10-22 (P-013 결정 제안 4·5·7과 작성자 질문, 리뷰어 "기준 자체의 문제"를 PM이 정리)
- **무엇을:**
  1. 4xx·5xx·비JSON 200을 포함한 **모든 HTTP 응답**을 `raw_api_responses`에 저장한다(차단 증거 보존, D-024). 읽는 쪽은 `latest_success()`(2xx만) 또는 `http_status` 필터를 써야 한다. 한계: 유니크 키가 `(request_hash, response_sha256)`이라 **본문 바이트가 같고 상태 코드만 다른 응답은 한 행으로 합쳐지고 먼저 저장된 `http_status`가 남는다**(리뷰어 재현). 빈 본문이나 공통 오류 JSON에서 생길 수 있다. 키 변경은 스키마 변경이라 실제로 문제가 될 때 사람 승인으로 다룬다.
  2. 403/429 차단은 실행을 **`aborted`**로 닫고 예외를 올린다(설계안 4장 그대로. P-013 브리핑의 `failed`는 PM 오류). 일반 예외는 `failed`. `aborted`는 "차단으로 멈춤"과 "코드 오류"를 구분해 준다.
  3. 재시도 대상 "일시적 오류"는 타임아웃·5xx·**연결 오류**(DNS 실패, 연결 거부 포함)다. 최대 3회(1·2·4초 + 지터)라 영구 오류여도 약 7초 뒤 실패한다. 리뷰어가 물은 "예시인가 전체 목록인가"에 대한 답: 이 세 가지가 전체 목록이다.
  4. raw `fetched_at`은 응답을 받은 순간의 **앱 시각**(테스트에서 주입 가능), `ingestion_runs`의 시각은 **DB `now()`**(CHECK `finished_at >= started_at`를 한 시계로 보장). 두 표의 시각을 서로 비교하지 않는다(D-030 교훈).
  5. `job_type` 값과 `code_version` 자동 기록은 P-016(CLI)에서 확정한다.
- **왜:** 각 항목의 근거는 PR #10 본문과 리뷰 보고서. 특히 1번은 티켓 기준 3 "모든 응답"과 B1(차단 증거)에서, 2번은 D-004(설계안이 계약)에서 나온다.
- **다른 선택지:** 2xx만 저장(차단 증거 소실), 차단도 `failed`(원인 구분 불가), 연결 오류는 즉시 실패(일시적 네트워크 흔들림에 취약), 둘 다 DB 시각(raw 받은 시각이 트랜잭션 시각과 어긋남).
- **후속(P-016 완료 기준에 반영, 리뷰어 [낮음] 1·3·4):** (a) `STALE_RUN_HOURS` 설정이 지금은 어디서도 쓰이지 않는다. CLI가 `track_run(stale_after_hours=settings.stale_run_hours)`를 넘기거나 기본값을 설정에서 읽게 해, 죽은 프로세스의 `running` 행이 이후 실행을 영구 거부하지 않게 한다. (b) `RunTracker.finish()`에 `WHERE status='running'`을 넣어 stale 정리로 닫힌 행이 `succeeded`로 되살아나지 않게 한다. (c) `httpx.DecodingError` 등 `TransportError` 밖의 httpx 예외도 `IngestionError`로 감싼다.

## D-033 방향 확정: 경기 전 전 경기 예측 + 가치 베팅 추천(가상 자금 시뮬레이터) + 정직한 성과 검증
- **날짜:** 2026-10-22 (사람 결정: "배팅을 직접 하는 게 아니라 가치 베팅을 찾아내고 가상 자금으로 수익률을 정직하게 검증하는 시스템. 경기 전에 전체 승패·언더오버를 예측해서 알려줘야 함")
- **무엇을:** `PRESAGIO_OVERVIEW.md`의 목표·비목표·단계 4~5를 바꾼다(PR #11, 2026-10-22 사람이 읽고 머지, `9468be5`).
  1. 경기 시작 전에 **그날 모든 경기**의 승패 확률과 예상 총점(언더/오버)을 낸다.
  2. 모델 확률과 마진을 제거한 시장 확률을 비교해 우위(edge)가 있으면 **가치 베팅을 추천**한다. 추천은 "경기, 마켓, 방향, 가상 스테이크"까지. 우위가 없으면 추천 없음.

- **다시 볼 때:** 단계 2 시작 시 세부 계획을 세울 때, 단계 4 시작 시 과거 배당 결정.

## D-034 games 적재 규칙: 일정이 진실, 게임로그는 상태·점수만, 이상한 경기는 빼고 partial
- **날짜:** 2026-10-22 (P-014, PR #12의 결정 제안 1~6 + 리뷰어 발견을 PM이 채택)
- **무엇을:**
  1. **일정(`ScheduleLeagueV2`)이 경기의 진실 소스.** 게임로그(`LeagueGameLog`)는 UPDATE 전용으로 `status_code`, `status_text`, `home_score`, `away_score`, `source`, `fetched_at`, `raw_response_id`만 갱신한다(설계안 6-1 표에 `leaguegamelog` 열 추가, v1.2). 일정에 없는 경기는 INSERT하지 않고 실패 항목 → `partial`.

## D-035 포제션 추정은 저장하지 않고 함수로 제공한다: `POSS ≈ FGA − OREB + TOV + 0.44 × FTA`, 경기 단위는 양 팀 평균
- **날짜:** 2026-10-22 (P-015, PR #13의 결정 제안 1 + "못 한 것" 1을 PM이 판단)
- **무엇을:** `presagio.ingestion.possessions.team_possessions(fga, oreb, tov, fta)` = `FGA − OREB + TOV + 0.44 × FTA`, `game_possessions` = 양 팀 평균. 입력이 하나라도 NULL이면 NULL. **DB에는 저장하지 않는다.** 승인된 설계안 6-2(D-028)가 "포제션은 저장하지 않는다(공식은 ML이 피처 버전으로, 단계 2)"라고 정했고, P-015 티켓 목표의 "계산해 넣는다"는 완료 기준(공식이 코드와 decisions에 적혀 있다)과 충돌하지 않으므로 설계안을 따른다. 단계 2 피처 모듈이 이 함수를 부르고 피처 버전으로 기록한다.
- **왜:** 입력 4개가 두 소스(게임로그, 박스스코어)에 모두 있고 단순해 설명하기 쉽다. 두 팀의 포제션은 거의 같으므로 평균이 한쪽 오차(팀 리바운드·팀 턴오버 누락)를 줄인다. 0.44는 Dean Oliver(*Basketball on Paper*, 2004)의 계수이고 basketball-reference의 TOV% 분모에도 쓰인다. 저장하지 않는 이유: 공식이 바뀌면(0.44 → 0.4, 리바운드 보정 추가) 저장값을 전부 다시 써야 하고, 피처 버전으로 두면 재현성이 보장된다.
- **주의:** TOV 정의가 소스마다 달라(게임로그는 팀 턴오버 포함 추정) 박스스코어 행으로 계산하면 경기당 약 1포제션 낮게 나온다. ML은 뷰 `team_game_stats_primary`(대표 = 게임로그)로 계산한다(D-028 A-6).
- **다른 선택지:** basketball-reference `Poss`(0.4 × FTA + 1.07 × 공격 리바운드 보정, 상대 DREB·FGM 필요. 더 정확하다고 알려졌지만 복잡. 브리핑의 "basketball-reference 근사"는 부정확한 표현이었고 작성자가 바로잡음), 0.475(대학 농구), 팀별 값만 쓰기, 컬럼 추가해 저장(스키마 변경, 재현성 약화).
- **다시 볼 때:** 단계 2에서 Four Factors·페이스 피처를 만들 때 공식 비교 실험을 `docs/experiments.md`에 남긴다.

- **날짜:** 2026-10-22 (P-016, PR #15의 결정 제안 8건 + 리뷰어 발견 1을 PM이 정리)
- **무엇을:**
  1. **단위:** `presagio backfill`의 적재 단위는 "날짜"가 아니라 **시즌 × 시즌 유형**(teams 1 + 시즌마다 일정 1 + 게임로그 유형별 1). `--from/--to`는 범위가 걸친 시즌을 통째로 같은 scope_key로 받고 부모 scope_key에 범위를 남기며 범위 안 경기 수를 출력한다. 완료 기준 3의 "날짜 단위"는 이 단위로 읽는다(D-023, B1).
  2. **재개:** 완료 단위는 건너뛴다. 완료 = **그 단위의 최신 run이 `succeeded`이고 시즌 종료(다음 해 10/15 UTC) 후에 시작**한 것. 최신이 `partial`/`failed`/`aborted`이거나 진행 중 시즌이면 다시 한다(upsert라 안전). `--force`면 전부 다시. (리뷰어 발견: "하나라도 succeeded"로 판정하면 `--force` 후 partial이 영구 skip → 최신 run 기준으로 수정.)
  3. **선행 실패:** 선행 단위가 이번 실행에서 실패했고 DB에 그 데이터도 없으면 뒤 단위는 `not_run`. 일부라도 있으면 진행.
  4. **종료 코드:** 0 전부 성공(건너뜀 포함), 1 하나라도 성공 아님(partial 포함) 또는 시작 전 오류, **2 차단(403/429)으로 즉시 중단**, 64 인자 오류(sysexits `EX_USAGE`, argparse 기본 2와 충돌 회피). 단계 6 스케줄러가 2를 보고 "오늘은 그만"으로 판단한다.
  5. **job_type 고정:** `teams`, `schedule`, `gamelog`, `boxscore`, `odds`, `odds_events`, `backfill`(부모), `incremental`(P-017). DB CHECK 없이 `start_run`이 파이썬에서 거부. `code_version`은 모든 run에 자동(`git rev-parse --short HEAD` → 패키지 버전 → NULL).
  6. **부모/자식:** `track_run` 블록 안에서 연 run은 `contextvars`로 자동 자식. 부모의 `api_calls`·`rows_written`은 0, 합계는 `error_detail.totals`(SUM 이중 계산 방지).
  7. **CLI는 argparse**(표준 라이브러리, 새 의존성 없음). `-v`는 서브커맨드 앞에서만. `--stale-after-hours`는 양수만.
  8. D-032 후속 반영: `track_run` 기본 `stale_after_hours`는 `STALE_RUN_HOURS`(모든 run이 시작 전 6시간 넘은 `running`을 정리), `finish()`는 `WHERE status='running'`(이미 닫힌 행은 경고 + False), `TransportError` 밖 httpx 예외는 재시도 없는 `IngestionError`, `httpx` 로거는 CLI가 WARNING 유지.
- **왜:** 호출을 날짜마다 하면 차단 위험이 수백 배다. 재개가 scope_key로 로더와 맞물려야 "끊겼다 이어 돌리기"가 호출을 아낀다. 종료 코드가 구분돼야 자동화(단계 6)가 차단과 실패를 다르게 다룬다.
- **다른 선택지:** 날짜별 ScoreboardV3 호출, 범위 scope_key로 부분 적재(시즌 성공 오인), 항상 전부 재처리(호출 낭비), typer(의존성 3개), DB CHECK로 job_type(값 추가마다 마이그레이션).
- **검증:** 리뷰어가 임시 DB에서 실제 2호출로 플레이오프 단위 적재, 재개·`--force`·403 즉시 중단·D-032 후속 4건 재현, 소켓 차단 상태 299 passed.
- **참고:** teams 단위는 아무 succeeded면 영구 skip이라 팀 확장·이전은 백필이 다시 받지 않는다 → P-017 매일 흐름에서 teams 갱신. 설치 이미지에 `.git`이 없으면 code_version이 패키지 버전만 남는다 → 단계 6에서 빌드 시 커밋 전달.

## D-039 매일 수집 규칙: 날짜 단위 scope_key, 성공 = 전 경기 종료 + 스탯 2행, 재시도 창 3일, 팀은 주 1회, 일정 전체는 주 1회 백필

## D-042 중립 경기장 경기는 일정 기준으로 적재하고, 로더 의미가 바뀌면 영향 단위를 `--force`로 다시 받는다
- **날짜:** 2026-10-23 (P-021, PR #19의 결정 제안 1·2 + 리뷰어 검증을 PM이 채택. 야간 위임 D-041)
- **무엇을:**
  1. **중립 경기장 처리:** `LeagueGameLog`는 중립 경기장 경기(멕시코시티·파리·베를린·런던·라스베이거스, NBA컵 준결승·결승)의 `MATCHUP`을 두 팀 모두 "X @ Y"로 준다. 이런 경기는 거부하지 않고 일정(`games`의 홈/원정)을 기준으로 두 행을 배정하며(D-034 2항과 같은 원리: 점수·스탯은 팀 ID로 붙임), `neutral_site` 품질 이슈로 기록한다. 이 판정은 MATCHUP 모양으로 **추정**한 것이고 일정의 `isNeutral`과 대조하지는 않는다. 리뷰어가 raw 14행 전체에서 정확히 10경기를 찾아 일정 `isNeutral=true`와 일치함을 확인했다. 2023-24는 `isNeutral`이 전부 false지만 `arenaCity`로 4경기를 식별할 수 있다.
  2. **로더 의미 변경 운영 규칙:** 로더가 "무엇을 저장하는가"를 바꾸는 PR(예: P-015가 게임로그 적재에 팀 스탯을 추가)은 PR 본문에 영향받는 단위를 적고, 머지 뒤 그 단위만 `presagio backfill ... --force`로 다시 받는다. 재개 규칙(D-037)은 옛 로더로 성공한 단위를 "끝난 것"으로 보기 때문이다(실제 사례: run 3으로 2025-26 플레이오프 팀 스탯이 0행이었음). 주의: `--season-type ... --force`는 teams와 그 시즌 일정까지 다시 받아 `games.source`가 바뀐다(force 범위가 단위보다 넓다). 장기적으로는 로더 버전을 run에 기록해 재개를 판단한다(단계 6 후보).
  3. **멱등성 판단 대상:** `games`·`team_game_stats` 행 수. raw 행은 소스가 같은 내용을 행 순서만 바꿔 줄 때 늘 수 있다(A-1의 바이트 기준 때문. 게임로그 동점 정렬).
- **왜:** 10경기(시즌당 3~5개)가 빠지면 팀 경기 수가 틀려 피처와 Elo가 어긋난다. 2026-27에도 중립 경기 3개가 예정되어 매일 수집에 필요하다. 일정이 진실이라는 원칙(D-034)을 그대로 적용한 것이라 새 원칙이 아니다.
- **다른 선택지:** 중립 경기는 버림(경기 수 누락), `isNeutral`을 보고 판정(일정 raw를 다시 읽어야 하고 2023-24는 플래그가 없음), 재개 규칙에 로더 버전 포함(지금은 과함, 단계 6).
