# 이 "회사"는 어떻게 돌아가나 (5분 요약)

## 왜 회사처럼 만들었나

Claude 세션 하나에 모든 걸 시키면 두 가지 문제가 생긴다.

1. **기억이 너무 길어진다.** 세션이 길어질수록 앞의 내용을 흐릿하게 기억하고 실수가 늘어난다.
2. **자기가 쓴 코드를 자기가 검사한다.** 사람도 그렇지만, 모델도 자기 코드의 문제를 잘 못 본다. 특히 "데이터 누수"처럼 티 안 나는 문제는 더 그렇다.

그래서 진짜 회사처럼 역할을 나눴다. 각 역할은 자기 영역만 보고, 다른 사람이 검사한다.

## 등장인물

- **너 (Founder):** 결정하고, PR을 읽고, 머지 버튼을 누른다. 코드를 짜지는 않지만 **이해는 해야 한다.**
- **PM:** 큰 일을 작은 티켓으로 쪼갠다. 작업자에게 "이거 해" 하고 브리핑을 쓴다. 결과가 왔을 때 "완료 기준을 다 채웠나"를 확인한다. 결정을 기록한다. 코드는 안 짠다.
- **작업자 (Data Engineer 등):** 티켓 하나를 받아 자기 브랜치에서 코드와 테스트를 짜고 PR을 연다. 티켓 하나가 끝나면 그 세션도 끝난다.
- **Reviewer:** PR을 받아 코드를 읽고, 테스트를 직접 돌려 보고, 문제를 보고서로 쓴다. 코드를 고치지는 않는다. 매번 새 세션이라 "아까 그 사람" 눈치를 안 본다.
- **Leakage Auditor (단계 2부터):** 리뷰어 중에서도 "시점 누수"만 전문으로 본다.

## 일이 흘러가는 모습

```
PM이 티켓을 고른다
  → PM이 브리핑을 쓴다 (처음 보는 사람도 일할 수 있게)
  → 작업자 세션이 새 브랜치에서 코드를 짠다
  → 작업자가 PR을 연다 (본문에 "어떻게 확인하나", "3문장 요약")
  → Reviewer 세션이 테스트를 직접 돌리고 보고서를 쓴다
  → PM이 완료 기준을 한 줄씩 대조한다
  → PM이 너에게 "3문장 요약 + 확인 명령 + 네가 물어볼 질문"을 준다
  → 네가 읽고, 질문하고, 머지한다
  → PM이 backlog를 DONE으로 바꾸고 결정을 기록한다
```

## 에이전트는 기억을 못 하는데 어떻게 이어지나

**모든 상태가 파일에 있다.** 할 일은 `docs/backlog.md`, 결정은 `docs/decisions.md`, 규칙은 `CLAUDE.md`, 결과는 PR 본문. 새 세션은 이 파일들을 읽고 시작한다. 그래서 "아까 말한 대로"는 금지고, 모든 브리핑은 처음 보는 사람 기준으로 쓴다.

비유하자면, 매일 아침 전 직원의 기억이 리셋되는 회사다. 그런 회사가 돌아가려면 문서가 완벽해야 한다. 그래서 문서 양식(`docs/team/handoff-templates.md`)이 엄격하다.

## 팀 사이에 어떻게 말을 맞추나

말을 안 맞춘다. 대신 **DB 테이블이 계약**이다. 데이터팀은 `games` 테이블을 채우고, ML팀은 그걸 읽기만 한다. ML팀이 `predictions`를 채우면 API팀이 읽기만 한다. 테이블 모양을 바꾸는 것만 네 승인이 필요하다. 이게 "사일로"가 서로 안 부딪히는 이유다.

## 네가 꼭 해야 하는 세 가지

1. PR 머지 전에 "3문장 요약"을 읽는다. 이해 안 되면 머지하지 않는다.
2. 머지 전에 PM에게 질문 하나를 한다. "왜 이렇게 했어?"면 충분하다.
3. 단계가 끝나면 학습 노트의 면접 질문에 문서 안 보고 답해 본다.

## 시작하는 법 (지금 당장)

1. 새 세션을 하나 연다.
2. `docs/team/workflow.md` 맨 아래 "PM 세션 시작 프롬프트"를 복사해서 붙여넣는다. 단계 번호는 0.
3. PM이 P-001 브리핑을 보여주면 읽고 "ㅇㅋ" 하면 된다. PM이 작업자 세션을 띄운다.
