# 용어집 (쉬운 말로)

> 모르는 단어가 나오면 여기서 찾는다. 단계가 진행되면 PM/Scribe가 계속 추가한다.
> 각 항목: **뜻 → 이 프로젝트에서 어디에 쓰이나 → 면접에서 한 문장으로**.

## 프로젝트 운영 용어

### 티켓 (Ticket)
- 한 세션이 끝낼 수 있는 크기의 일 하나. 목표, 범위, 완료 기준이 적혀 있다.
- `docs/backlog.md`에 P-001 같은 번호로 있다.
- "일을 작게 쪼개서 검증 가능한 완료 기준과 함께 관리했습니다."

### 완료 기준 (Acceptance Criteria)
- "이게 되면 끝"을 검증 가능한 문장으로 쓴 것. 예: "`uv run pytest`가 통과한다."
- 사람만 바꿀 수 있다. 리뷰어가 이걸 기계적으로 대조한다.
- "완료 기준을 명령과 예상 결과로 적어서 '거의 됐다'가 끼어들 틈을 없앴습니다."

### 브리핑 / 핸드오프 (Handoff)
- 일을 넘길 때 주는 설명 문서. 받는 사람이 아무것도 모른다고 가정하고 쓴다.
- 에이전트는 세션마다 기억이 리셋되므로 브리핑 품질이 곧 결과 품질이다.

### 스파이크 (Spike)
- 코드를 짜기 전에 "이게 되나?"를 짧게 조사하는 티켓. 산출물은 코드가 아니라 보고서.
- P-010(nba_api 조사), P-018(배당 API 조사)이 스파이크다.
- "불확실한 외부 의존성은 구현 전에 스파이크로 먼저 확인했습니다."

### ADR (Architecture Decision Record, 설계 결정 기록)
- "무엇을 / 왜 / 다른 선택지"를 짧게 적은 기록. `docs/decisions.md`의 D-001 같은 항목.
- 면접 질문 대부분이 여기서 나온다.

### 사일로 (Silo)
- 원래는 "부서끼리 담 쌓고 소통 안 한다"는 나쁜 뜻. 여기서는 일부러 영역을 나누고, 영역 사이를 DB 스키마라는 계약으로만 연결한다는 뜻으로 쓴다.

### 앵커링 (Anchoring)
- 먼저 들은 의견에 판단이 끌려가는 현상. "이거 맞지?"라고 물으면 "맞다"고 하기 쉽다.
- 그래서 리뷰어에게 작성자 결론을 안 준다.

## Git / 협업 용어

### 브랜치 (Branch) / PR (Pull Request)
- 브랜치는 "main을 건드리지 않고 따로 작업하는 복사본". PR은 "이 브랜치를 main에 합쳐 달라"는 요청이고, 그 화면에서 리뷰가 이뤄진다.
- 모든 코드 변경은 브랜치 → PR → 리뷰 → 머지.

### worktree
- 한 레포를 폴더 여러 개로 동시에 열어두는 git 기능. 세션마다 자기 폴더가 생겨서 서로 파일을 덮어쓰지 않는다.

### squash merge
- PR의 커밋 여러 개를 하나로 뭉쳐서 main에 넣는 방식. main 히스토리가 "티켓 하나 = 커밋 하나"로 깔끔해진다.

### Conventional Commits
- 커밋 제목을 `feat(ingestion): ...`, `fix(db): ...`처럼 "종류(영역): 설명" 형식으로 쓰는 관례. 나중에 변경 이력을 기계로도 읽을 수 있다.

### pre-commit 훅
- 커밋 직전에 자동으로 도는 검사. 여기서는 ruff(린트/포맷)와 비밀값 탐지를 돌린다. API 키를 실수로 커밋하는 사고를 막는다.

## 데이터 파이프라인 용어

### raw 레이어 / clean 레이어
- raw는 외부 API 응답을 **받은 그대로** 저장한 것. clean은 그걸 우리가 쓰기 좋은 표 모양으로 정리한 것.
- raw를 남기는 이유: 정리 코드에 버그가 있어도 API를 다시 부르지 않고 raw에서 다시 만들 수 있다. 외부 API가 막혀도 데이터가 남는다.
- "원본 응답을 보관해서 재처리 가능성을 확보했습니다."

### 멱등성 (Idempotency)
- 같은 작업을 1번 하든 10번 하든 결과가 같은 성질. 백필을 중간에 끊고 다시 돌려도 중복이 안 생겨야 한다.
- 구현 방법은 보통 **upsert**(있으면 갱신, 없으면 삽입)와 유니크 제약.
- "수집 작업을 멱등하게 만들어서 재실행과 장애 복구가 안전합니다."

### upsert
- update + insert. "이 키의 행이 있으면 갱신하고 없으면 넣어라." PostgreSQL에서는 `INSERT ... ON CONFLICT DO UPDATE`.

### 백필 (Backfill) / 증분 수집 (Incremental)
- 백필은 과거 데이터를 한꺼번에 채우는 것(3시즌). 증분은 매일 새로 생긴 것만 더하는 것(어제 결과, 오늘 일정).

### 지수 백오프 (Exponential Backoff)
- 실패하면 1초, 2초, 4초... 점점 길게 기다렸다가 재시도하는 방식. 상대 서버를 더 괴롭히지 않으면서 일시적 오류를 넘긴다.
- 429(너무 많은 요청)나 5xx(서버 오류)에만 재시도하고, 404 같은 건 바로 포기한다.

### 타임아웃 (Timeout)
- "이 시간 안에 응답 없으면 포기". 없으면 외부 서버가 멈췄을 때 우리 프로그램도 영원히 멈춘다.

### ingestion_runs
- "언제 무슨 수집 작업을 돌렸고 성공했나 실패했나 몇 건 처리했나"를 적는 테이블. 운영 로그의 DB 버전. 단계 6의 `/health`와 신선도 체크가 이걸 읽는다.

### 데이터 품질 체크 (Data Quality Check)
- 데이터가 상식에 맞는지 자동으로 검사. "경기당 팀은 2개", "두 팀 득점 합 = 최종 점수" 같은 것.

### Alembic / 마이그레이션 (Migration)
- DB 테이블 모양을 바꾸는 변경을 코드 파일로 남기고 순서대로 적용하는 도구. "스키마의 git".
- 마이그레이션 없이 손으로 테이블을 바꾸면 다른 환경(CI, 배포 서버)에서 재현이 안 된다.

### ORM (SQLAlchemy)
- 파이썬 클래스로 테이블을 표현하고 SQL을 대신 써 주는 라이브러리.

### 픽스처 (Fixture) / mock
- 픽스처는 테스트용으로 저장해 둔 샘플 데이터(예: 실제 API 응답 JSON 하나). mock은 진짜 외부 서비스 대신 가짜로 응답해 주는 장치.
- 테스트가 네트워크를 타지 않게 하려고 쓴다. 테스트는 빠르고, 오프라인에서도 돌고, 외부 서비스가 바뀌어도 깨지지 않는다.

### UTC
- 시간대가 없는 세계 표준 시각. DB에는 항상 UTC로 저장하고, 보여줄 때만 한국시간으로 바꾼다. 미국 경기는 한국시간으로 "다음 날 아침"이라 이걸 안 지키면 날짜가 꼬인다.

## 모델링 / 평가 용어 (단계 2부터 자세히 추가)

### as_of / 데이터 누수 (Data Leakage)
- as_of는 "이 시점 기준으로"라는 뜻. 어떤 경기를 예측할 때 그 경기 시작 전까지의 정보만 써야 한다.
- 누수는 미래 정보가 몰래 섞여 들어가는 것. 예: 경기 당일 결과가 "최근 5경기 평균"에 포함되는 off-by-one 실수. 누수가 있으면 성능이 거짓으로 좋아 보인다.
- "모든 피처 함수가 as_of를 받고, 미래 데이터를 넣어도 과거 예측이 안 변하는 테스트로 누수를 막았습니다."

### walk-forward 평가
- 시간 순서대로 "이 날까지 데이터로 학습 → 다음 날 예측"을 반복하는 평가. 실제 운영과 같은 조건이라 정직하다.
- 반대는 무작위 train/test 분할. 미래 경기로 학습해서 과거를 맞추는 셈이라 금지.

### 기준선 (Baseline)
- "항상 홈팀 승"처럼 아주 단순한 예측. 복잡한 모델이 이걸 못 이기면 의미가 없다.

### Elo 레이팅
- 체스에서 온 실력 점수. 이기면 오르고 지면 내리는데, 약팀을 이기면 조금, 강팀을 이기면 많이 오른다. 두 팀 점수 차이로 승률을 계산할 수 있다. 홈 어드밴티지와 시즌 사이 평균 회귀를 넣어 쓴다.

### log loss / Brier score
- 둘 다 "확률 예측이 얼마나 좋았나"를 재는 점수. 정확도는 "70%라고 했든 51%라고 했든 맞으면 1점"이지만, 이 둘은 자신감이 틀렸을 때 벌점을 준다. 낮을수록 좋다.

### 보정 (Calibration)
- "70%라고 예측한 경기들이 실제로 70% 정도 이겼나"를 보는 것. reliability diagram은 그걸 그래프로 그린 것.

### 시장 확률 (Market-implied Probability) / 마진 제거
- 배당을 확률로 바꾼 것. 배당 2.0은 50%. 그런데 북메이커는 수수료(마진) 때문에 양쪽 확률 합이 100%를 넘게 만든다. 그 초과분을 비례로 빼서 합이 100%가 되게 하는 게 마진 제거.
- 이 프로젝트에서 배당은 **오직 비교 기준**으로만 쓴다. 베팅 기능은 없다.

### 페이스 (Pace) / 공격·수비 효율 (Offensive/Defensive Rating)
- 페이스는 경기당 공격 횟수(포제션 수). 효율은 100포제션당 득점/실점. 득점을 그대로 비교하면 빠른 팀이 유리해 보여서, 포제션당으로 정규화한다.

### 백투백 (Back-to-back)
- 이틀 연속 경기. 피로 때문에 성적이 떨어지는 경향이 있어 피처로 쓴다.

## 데이터 파이프라인 용어 (단계 1에서 추가)

### 멱등성 (Idempotency)
- 같은 작업을 두 번 해도 결과가 한 번 한 것과 같은 성질. 이 프로젝트의 모든 적재는 멱등하다.
- `INSERT ... ON CONFLICT` 로 구현. 테스트가 "두 번 적재 후 행 수 동일"을 확인한다.
- "재실행이 안전하도록 모든 쓰기를 멱등하게 만들고 테스트로 증명했습니다."

### upsert
- "있으면 갱신, 없으면 삽입"을 한 문장으로 하는 DB 명령. PostgreSQL의 `INSERT ... ON CONFLICT DO UPDATE`.
- 유니크 키가 "무엇이 같은 행인가"를 정의하므로, 유니크 키 설계가 곧 멱등성의 근거다.

### raw / clean 레이어
- raw: 외부 응답을 받은 그대로(JSON) 보관하는 표. 나중에 다시 정제할 수 있고 "그때 뭘 받았나"의 증거.
- clean: 우리가 쓰기 좋게 정리한 표(`games`, `team_game_stats` 등). 모든 clean 행에는 `fetched_at`(받은 시각)과 `source`(어디서)가 있다.

### as_of (기준 시각)
- "이 시각까지 알 수 있던 정보만 쓴다"의 그 시각. 피처 함수는 반드시 `as_of`를 입력받는다.
- 누수(미래 정보 사용)를 막는 핵심 장치. 단계 2에서 본격 사용.

### 마이그레이션 (Migration, Alembic)
- DB 구조 변경을 번호 붙인 파일로 쌓는 것. `0001`이 처음 표를 만든다. 어느 컴퓨터에서든 순서대로 적용하면 같은 DB가 된다.
- `uv run alembic upgrade head`(올리기), `downgrade base`(되돌리기).

### service container (CI)
- GitHub Actions 잡이 돌 때 옆에 잠깐 띄우는 도커 컨테이너. 잡이 끝나면 사라져 매번 빈 DB로 시작한다.
- 덕분에 CI가 진짜 PostgreSQL로 테스트를 돌린다(D-029).

### worktree
- 같은 git 저장소를 다른 폴더에 한 번 더 체크아웃한 것. 작업자마다 전용 worktree에서 일해 서로 파일을 덮어쓰지 않는다.

### 포제션 (Possession)
- 한 팀이 공격권을 가진 횟수. 추정식 `FGA − OREB + TOV + 0.44 × FTA`. 공격·수비 효율(100포제션당 득점)과 페이스의 기초.
- 저장하지 않고 함수로 계산한다(D-035).

### 암시 확률과 마진 (Implied probability, Vig)
- 소수식 배당 2.0 → 암시 확률 1/2.0 = 50%. 두 쪽 암시 확률의 합이 100%를 넘는 만큼이 북메이커 마진. 마진을 비례로 빼면 "시장이 보는 확률"이 된다.

### 마감 배당 (Closing line)
- 경기 시작 직전의 마지막 배당. 시장 정보가 가장 많이 반영된 가격이라 평가 기준점으로 쓴다.
- 우리는 컬럼이 아니라 뷰(`odds_closing_lines`)로 "시작 전 마지막 스냅숏"을 고른다(A-8).

### CLV (Closing Line Value)
- 내가 걸었을 때 가격이 마감 가격보다 유리했는가. 꾸준히 양수면 진짜 우위, ROI는 운에 속기 쉽다.

### 가치 베팅 / 우위 (Value bet, Edge)
- 내 추정 확률이 시장 암시 확률보다 높은 쪽. 그 차이가 edge. 우위가 없으면 "추천 없음"이 정답(D-033).

### partial (부분 성공)
- 실행 기록 상태 중 하나. "대부분 됐는데 몇 개는 못 했다". 실패 목록이 남아 다음 실행이 그것만 다시 한다. 조용히 성공으로 닫는 것보다 정직하다(D-034).
