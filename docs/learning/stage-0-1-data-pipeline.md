# 단계 0~1 학습 노트: 작업실 꾸미기와 데이터 창고 짓기

> 작성: PM, 2026-10-22 밤(초안). P-021 실제 백필 숫자는 보고서가 오면 채운다(아래 `TBD`).
> 읽는 사람: 이 프로젝트를 만든 본인. 목표는 면접에서 "왜 이렇게 만들었나"를 자기 말로 말하는 것.

## 이 단계에서 만든 것 (한 문단, 쉬운 말)

단계 0은 **작업실 꾸미기**였다. 누가 레포를 받아도 명령 한 줄로 똑같은 파이썬 환경이 깔리고(`uv sync`), 커밋할 때마다 자동으로 코드 검사와 비밀값 검사가 돌고(pre-commit), DB가 상자 안에서 뜨고(`docker compose up`), PR을 올리면 GitHub가 알아서 테스트를 돌린다(CI). 단계 1은 **데이터 창고 짓고 채우기**였다. NBA 공식 통계와 배당 API를 실제로 호출해 "뭘 주는지" 확인하고(조사), 담을 표를 설계해 승인받고(스키마), 표를 만들고(마이그레이션), 모든 외부 호출이 지나는 관문을 만들고(수집 레이어), 팀·경기·스탯·배당을 넣는 코드를 만들고(어댑터·로더), 그걸 `presagio backfill`(과거 채우기), `presagio ingest-daily`(매일 갱신), `presagio quality-check`(검사) 세 명령으로 묶었다. 마지막으로 실제 3시즌을 받아 창고를 채웠다(P-021).

## 중요한 결정과 이유 (D-번호는 `docs/decisions.md`)

- **역할을 나눈 에이전트 회사로 운영 (D-001, D-005, D-006).** 작성자와 리뷰어를 분리하고, 리뷰어에게 작성자의 결론을 주지 않는다. 실제 효과: 리뷰어가 "추측으로 적은 한계"를 여러 번 잡아냈다(gitleaks 검사 범위, 비밀번호 노출, 시계 의존 테스트, 연기 경기 마감 배당). 다른 선택지는 한 세션이 다 하기(검증 독립성 없음).
- **비밀값은 두 겹으로 막는다 (D-012, D-015).** 커밋 직전 gitleaks + CI에서 기록 전체 검사. 한 겹(pre-commit)은 `--no-verify`로 우회되기 때문.
- **파이썬은 uv가 관리하는 3.12만 (D-013).** 이 맥의 anaconda 파이썬이 먼저 잡히는 문제를 `only-managed`로 막았다.
- **스키마가 팀 사이의 계약 (D-004, D-028).** 데이터팀과 ML팀은 표로만 대화한다. 승인된 설계안(`docs/design/schema-v1.md`)과 마이그레이션이 같은지 테스트가 비교한다(D-030).
- **시각은 UTC 필드만, 경기 유형은 ID 3번째 자리 (D-025).** NBA 응답의 `*Est` 필드는 Z가 붙어 있지만 동부 시각이라 속기 쉽다. 4시즌 5,470경기에서 ID 규칙 위반 0.
- **일정이 진실, 게임로그는 점수만, 이상한 경기는 빼고 partial (D-034).** 한 경기 때문에 시즌 전체가 멈추면 안 되고, 누락을 "성공"으로 닫으면 재개 로직이 영원히 빠뜨린다.
- **포제션은 저장하지 않고 함수로 (D-035).** 공식이 바뀌면 저장값을 전부 다시 써야 한다. 피처 버전으로 두면 재현성이 남는다.
- **배당: 긴 형식, 시작한 경기 배당은 버림, 매핑은 후보 1개일 때만 (D-036).** 경기 중 배당을 "예측 시점 배당"으로 쓰면 미래 정보가 섞인다(누수).
- **백필 단위는 날짜가 아니라 시즌×시즌 유형 (D-037).** 날짜마다 호출하면 차단 위험이 수백 배. 재개는 "최신 실행이 성공"일 때만 건너뛴다.
- **매일 수집은 한국 16:00 (D-038).** 원래 문서의 "한국 오전, 미국 경기 종료 후"는 동시에 성립하지 않았다(한국 09:00 = 동부 전날 20:00, 경기 중).
- **방향: 실제 베팅 없이 가치 베팅 추천 + 가상 자금 검증 (D-033).** 시장을 기준선으로 두고 "시장이 틀리는 지점"을 찾는다. 우위가 없으면 "추천 없음"이 정답.

## 어려웠던 것과 해결

- **"로컬에서 되는데요."** Docker Desktop은 VM 위라 DB 시계가 호스트보다 1ms쯤 느리다. 그 1ms가 "파이썬 시각 vs DB 시각" 비교 테스트의 버그를 가렸고, CI(시계 공유)에서는 거의 매번 실패할 뻔했다. 리뷰어가 CI 조건을 흉내 내 잡았다. 교훈: 시각은 한쪽(DB 또는 고정값)으로 통일하고, 로컬 흉내는 CI 증명을 대신하지 못한다(D-030).
- **nba_api 라이브러리는 받은 바이트를 안 준다.** 상태 코드를 보기 전에 JSON으로 파싱해 버려서 차단 페이지(HTML 403)가 파싱 예외로 둔갑한다. 그래서 라이브러리는 "어떤 URL에 뭘 보내는지"만 빌리고 전송은 우리 httpx가 한다(D-031).
- **같은 스탯이 엔드포인트마다 다르다.** 시즌 기록의 턴오버(팀 턴오버 포함)와 박스스코어의 턴오버(선수 합)가 1씩 다르다. 소스별로 따로 저장하고 대표를 하나로 고정했다(A-6).
- **연기된 경기의 마감 배당.** 경기가 이틀 미뤄지면 뷰가 연기 전 배당을 "마감"으로 내줄 뻔했다. 설계 리뷰에서 임시 DB로 재현해 고쳤다(A-8).
- **세션 띄우기 제약.** 앱이 "사람이 클릭해야" 세션을 띄우는 턴이 있어서, PM이 카드를 올리고 사람이 클릭하는 방식과 서브에이전트 대체를 썼다.

## 실패한 시도 (있으면)

- P-002 첫 수정에서 "설정이 틀리면 실패"로 바꾸자 실패 경로가 비밀번호를 평문으로 찍었다(pytest가 함수 인자를 출력). URL 객체 + traceback 숨김으로 두 겹으로 막았다.
- P-014 첫 버전은 한 경기의 값이 이상하면 시즌 전체 적재가 실패했다. 그 경기만 빼고 partial로 바꿨다.
- P-016 첫 버전은 "성공한 적이 한 번이라도 있으면 건너뜀"이라 `--force` 뒤 partial을 다시 시도하지 않았다. 최신 실행 기준으로 바꿨다.

## 면접 예상 질문 3개와 모범 답

1. **"외부 API를 쓸 때 어떤 점을 신경 썼나요?"**
   답: 모든 호출이 한 관문을 지나게 했습니다. 요청 간격 1초, 타임아웃 10초, 일시 오류만 지수 백오프 재시도, 403/429는 즉시 중단, 그리고 받은 응답은 바이트 지문과 함께 원본으로 보관합니다. 라이브러리가 상태 코드 전에 파싱해 버리는 걸 발견해서 전송은 직접 하도록 바꿨고, 차단 응답이 파싱 예외로 숨는 걸 테스트로 막았습니다.
2. **"같은 작업을 두 번 돌려도 안전한가요?"**
   답: 네. 모든 쓰기는 유니크 키 기준 upsert라 두 번 돌려도 행 수가 같고, 원본 응답은 내용이 같으면 새 행 없이 횟수만 올립니다. 백필은 단위별 실행 기록을 보고 끝난 단위를 건너뛰며, 테스트가 "두 번 적재 후 행 수 동일"을 직접 확인합니다.
3. **"데이터 누수를 어떻게 막았나요?"**
   답: 설계 단계부터입니다. 모든 행에 수집 시각이 있고, 경기 시각은 UTC로만 저장하며, 배당은 시각별 스냅숏으로 쌓되 경기 시작 후 배당은 아예 저장하지 않습니다. 마감 배당도 컬럼이 아니라 "시작 전 마지막 스냅숏"이라는 규칙(뷰)으로 뽑아서 정의를 나중에 바꿀 수 있게 했습니다. 피처 계산은 기준 시각(as_of)을 받게 설계했고, 단계 2부터는 독립 감사 역할이 이를 검증합니다.
